## 1. 面试官真正想问什么？

这道题表面是在问“Agent 中断了怎么办”，本质考的是：

> 一个生产级 Agent 在长任务、多轮工具调用、流式输出、外部副作用、上下文压缩和运行时故障下，如何做到可停止、可恢复、可观测、可解释。

不要只回答“重试一下 / 重新拉起 / 保存上下文”。面试官更想听到这些点：

- 你能不能把中断原因按层次拆开，而不是全怪模型。
- 你是否知道 Agent Loop、Tool Pipeline、Context、State、Harness 都会导致中断。
- 你是否理解恢复不能盲目继续，要先重新观察事实状态。
- 你是否知道有副作用工具需要幂等设计和两阶段提交。
- 你是否能讲清楚中断后的用户体验、日志审计和恢复边界。

一句话：

> Agent 中断不是单点异常，而是长任务系统的常态；恢复能力要靠 Runtime 和 Harness 设计，而不是靠模型“记得继续”。

---

## 2. 1 分钟回答

如果 Agent 中断，我会先从五层分析原因：

第一是 **模型层**，比如模型 API 超时、限流、流式响应断开、tool call 参数生成不完整。  
第二是 **Agent Loop 层**，比如超过最大轮次、重复工具调用触发熔断、token 预算耗尽，或者用户主动停止。  
第三是 **Tool Pipeline 层**，比如工具参数错误、权限审批未通过、handler 超时、外部 API 失败，或者工具返回过大。  
第四是 **Context 层**，比如上下文爆掉、压缩丢了关键状态、旧状态污染当前判断。  
第五是 **Runtime / Harness 层**，比如 WebSocket 断开、进程重启、任务状态没持久化、多 Agent 并发写冲突。

恢复时不能直接让模型“继续上次动作”，而要先恢复任务状态，再重新观察当前事实：任务目标是什么、已完成哪些步骤、最近一次工具调用有没有副作用、外部资源现在是什么状态。如果涉及写文件、发消息、提交代码、调用外部 API 这类副作用操作，要用服务端生成的 `retry_group_id` 或 idempotency key 做幂等恢复，判断已执行、未执行还是不确定。

最后要把恢复结果结构化反馈给用户：中断发生在哪一层、当前状态是否安全、哪些步骤已完成、下一步能否自动继续，还是需要用户确认。

## 3. 深入回答：中断原因怎么分层分析？

### 3.1 模型层中断

常见原因：

- 模型 API 超时或服务端 5xx。
- 被限流，触发 429 / Retry-After。
- 流式响应中断，只收到部分 token。
- tool call 参数还没生成完整，JSON 不可解析。
- 模型输出过长，被 `max_tokens` 截断。
- stop reason 异常，比如 length、content_filter、error。

解决方案：

- 对错误分类，而不是无脑 retry。
- 网络 / 5xx 可以有限重试 + 指数退避。
- 429 要尊重 `Retry-After`。
- 输出截断可以走“继续生成”，但要限制继续次数。
- tool call 参数不完整时禁止执行工具，必须等 schema 校验通过。
- 流式不稳定时可以降级成非流式。

面试表达：

> 流式文本中断可以保留已生成内容，但流式 tool call 中断不能直接执行，因为参数可能是不完整 JSON。工具执行安全优先于体验。

---

### 3.2 Agent Loop 层中断

常见原因：

- 超过最大工具调用轮次。
- 超过最大运行时间。
- token 预算耗尽。
- 模型反复调用同一个失败工具，触发 loop detection。
- Ping-Pong 式无进展对话。
- 用户主动 stop / cancel。
- Hook 主动拦截。

解决方案：

- 设计明确退出路径：正常完成、异常失败、用户停止、熔断停止。
- 加步数熔断、时间熔断、token 熔断、重复调用熔断。
- 对最近 N 步工具名、参数、错误摘要做指纹检测。
- 按 Warning / Critical / Break 分级：先提醒模型换策略，严重时直接停止。
- 熔断后输出“为什么停”和“当前可恢复状态”。

面试表达：

> Agent Loop 通常是开放式的，因为工具轮次不可预设；但开放式不等于无限执行，外层 Harness 必须保证它能停下来。

---

### 3.3 Tool Pipeline 层中断

常见原因：

- 参数格式错误：字段缺失、类型不对、JSON 解析失败。
- 业务校验失败：路径不存在、资源状态不允许操作、目标 ID 无效。
- 权限不足：高风险工具需要用户审批。
- 工具执行超时：搜索、构建、测试、外部 API 长时间无响应。
- 工具结果过大：日志、网页、diff、检索结果超过上下文预算。
- 外部副作用状态未知：请求发出后连接断了，不知道成功还是失败。

解决方案：

- 工具执行前：格式校验 → 业务校验 → 权限校验 → 资源配额 → 副作用门控。
- 工具执行中：超时控制、取消信号、资源限制。
- 工具执行后：结果过滤、脱敏、截断、摘要化、完整日志落盘。
- 对临时错误做有限重试；对业务错误和权限错误不要盲目重试。
- 对有副作用工具使用幂等 ID 和两阶段提交。

面试表达：

> 模型输出只是意图，不是可信命令。真正能不能执行，要由 Tool Pipeline 和权限系统决定。

---

### 3.4 Context Engineering 层中断

常见原因：

- 上下文超过模型窗口。
- 工具结果太长导致上下文污染。
- 历史裁剪切断了 tool call / tool result 配对。
- 压缩摘要丢了关键 ID、路径、失败原因、权限状态。
- Memory 或旧 transcript 与当前事实冲突。
- 多轮任务里模型遗忘最初目标，开始跑偏。

解决方案：

- 先压缩最大噪声源：工具结果。
- 长日志 / diff / 搜索结果只放摘要，完整内容落盘并保留引用。
- 裁剪历史时保护最近 N 轮和工具调用配对关系。
- LLM 摘要要结构化，必须保留：目标、当前步骤、已完成、失败原因、关键 ID、权限状态、下一步。
- 恢复后重新注入当前工作集。
- 记忆和当前工具观察冲突时，以当前观察为准。

面试表达：

> Context Engineering 的目标不是“压得越短越好”，而是压缩后仍然能恢复当前任务状态。

---

### 3.5 Runtime / Harness 层中断

常见原因：

- 前端页面刷新、WebSocket 断开、客户端掉线。
- Agent 进程崩溃或 Gateway 重启。
- 后台任务被系统 kill。
- session 状态只存在内存，没有持久化。
- 多 Agent 并发写同一个文件 / 数据库 / 远程资源。
- 权限审批状态丢失。
- 日志不足，无法判断中断点。

解决方案：

- 任务状态持久化：task ID、session ID、用户目标、计划、当前步骤、上下文摘要。
- 事件日志：记录模型输出、工具调用、工具结果、权限事件、异常和恢复动作。
- 后台任务和前端连接解耦：客户端断了不等于任务必须死。
- 写操作串行化，多 Agent 写共享资源要走锁、队列或 worktree 隔离。
- 恢复时先读取状态，再重新观察外部事实。
- 不确定状态要请求人工确认，而不是强行继续。

面试表达：

> Harness 负责把模型包在一个可靠运行环境里。连接中断只是 UI 层现象，真正关键是任务状态有没有持久化、外部副作用能不能恢复。

## 4. 中断后如何恢复？标准流程

可以按 6 步回答：

### Step 1：识别中断类型

先判断是：

- 用户主动中断。
- 模型 API 中断。
- 工具执行中断。
- Agent Loop 熔断。
- Runtime / 网络连接中断。
- 进程崩溃或重启。

不同中断类型决定后续能不能自动恢复。

---

### Step 2：加载持久化状态

恢复时要加载：

- task / session ID。
- 用户原始目标。
- 当前计划和步骤状态。
- 最近工具调用与结果。
- 上下文摘要。
- 权限审批状态。
- 幂等 ID / 外部资源 ID。
- 已生成但未确认的输出。

如果没有持久化状态，只能基于 transcript 做弱恢复，可靠性会差很多。

---

### Step 3：重新观察当前事实

恢复不能只相信历史记录，要重新查询当前状态。例如：

- 文件是否已经被修改。
- 数据库记录是否已经创建。
- 消息是否已经发送。
- Git commit / push 是否已经完成。
- 外部任务是否仍在运行。
- 用户是否已经发了新的指令。

原则：

> 历史状态负责告诉我们“当时想做什么”，当前观察负责告诉我们“现在事实是什么”。冲突时优先相信当前事实。

---

### Step 4：判断副作用状态

对有副作用的工具，要判断：

| 状态 | 含义 | 处理 |
|---|---|---|
| 已执行 | 外部事实证明操作成功 | 标记完成，继续下一步 |
| 未执行 | 外部事实证明没有发生 | 可以按幂等 ID 重试 |
| 不确定 | 查不到或状态冲突 | 停止并请求用户确认 / 人工介入 |

关键是不要盲目重试。

例如“发送消息”中断，如果直接再发一次，可能重复打扰别人；“创建订单”中断，如果直接再建一次，可能重复扣费；“git commit”中断，如果直接再 commit，可能生成重复提交。

---

### Step 5：重建上下文和计划

恢复给模型的上下文应该是结构化的，而不是把全部旧聊天塞回去：

```txt
当前目标：...
已完成：...
当前步骤：...
中断点：...
最近工具结果：...
外部事实观察：...
已尝试失败方案：...
权限状态：...
下一步候选：...
禁止重复：...
```

这能避免模型恢复后重复踩坑。

---

### Step 6：继续、降级或停止

最后根据风险选择：

- **自动继续**：只读任务、无副作用、状态清晰。
- **幂等重试**：有副作用但 idempotency key 能确认未执行。
- **降级处理**：模型 API 不稳定时换 provider / 非流式 / 小范围任务。
- **请求确认**：外部副作用不确定、权限状态不清、高风险写操作。
- **安全停止**：重复失败、状态冲突、恢复信息不足。

## 5. 典型场景题

### Q1：Agent 输出到一半断了，怎么办？

如果只是文本输出中断，可以保留已输出内容，标记为 partial，然后基于已有上下文继续生成。

但如果是在 tool call 参数生成过程中中断，不能执行这个工具。因为 Function Calling 的参数可能还没闭合，schema 校验也没通过。要么重新请求模型生成完整 tool call，要么让模型改用文本解释。

---

### Q2：工具调用发出去了，但连接断了，怎么办？

这是最典型的恢复难点。要看工具有没有副作用。

如果是只读工具，比如搜索、读取文件、查询状态，通常可以重试。

如果是写操作，比如发消息、写数据库、提交代码、创建资源，就不能盲目重试。执行前应该有 `retry_group_id` 或 idempotency key。恢复时先查询外部状态，判断这次操作到底有没有成功。

---

### Q3：Agent 被用户手动 stop，恢复时能不能自动继续？

一般不能默认自动继续。

用户主动 stop 是一种明确控制信号，恢复时最多给出当前状态和可继续选项。除非用户再次确认“继续”，否则不应该自动执行后续工具，尤其是写操作。

---

### Q4：Agent 因为上下文过长中断，怎么办？

先做上下文压缩，而不是简单删除历史。

优先压缩工具结果，保留摘要和完整日志引用；然后裁剪旧轮次，保护最近对话和 tool call / tool result 配对；最后做结构化摘要。恢复上下文必须包含目标、当前步骤、关键 ID、失败原因、已尝试方案和下一步。

---

### Q5：Agent 反复失败后中断，是否应该继续重试？

不应该无限重试。

要看失败是否同类重复。如果最近 N 次工具名、参数和错误摘要高度相似，说明模型没有产生新策略，应触发 loop detection。低风险可以提示模型换思路，高置信度重复要熔断，并把失败原因反馈给用户。

---

### Q6：Agent 进程重启后，如何恢复长任务？

需要任务状态持久化，而不是只依赖内存。

恢复时先加载 task state，包括用户目标、计划、已完成步骤、最近工具调用、幂等 ID、权限状态和上下文摘要。然后重新查询外部事实，确认文件、资源、远程状态是否和记录一致。最后再决定继续、重试或请求确认。

---

## 6. 项目中怎么讲

如果你要把这个题和自己的项目结合，可以这样说：

> 在我的设计里，Agent 每个任务都会有 task_id。Agent Loop 每一步都会写事件日志，包括模型输出、工具调用、工具结果、权限审批和异常。工具层对读写操作做风险分级：读操作可以自动重试，写操作需要副作用门控。对于发消息、写数据库、提交代码这类操作，会使用服务端生成的 retry_group_id 做幂等恢复。中断后 Recovery Manager 会先加载 task state，再重新观察外部事实，比如文件状态、数据库记录或远程资源状态，判断操作已完成、未完成还是不确定。最后再把一个结构化恢复上下文交给模型继续执行。

可以补一句工程取舍：

> 不是所有任务都值得完整恢复。低风险短任务可以失败后重跑；长任务、高成本任务、带外部副作用任务，才需要完整的状态持久化和幂等恢复。

## 7. 高频追问

### 追问 1：中断恢复时最重要的原则是什么？

不要盲目继续，要先重新观察当前事实；历史记录负责恢复意图，当前事实负责判断状态。

### 追问 2：为什么不能直接重试上一次工具调用？

因为上一次工具可能已经执行成功，只是结果没返回。对有副作用工具，直接重试可能造成重复发送、重复创建、重复提交或数据污染。

### 追问 3：哪些工具中断后可以直接重试？

只读、无副作用、幂等的工具通常可以重试，比如搜索、读取文件、查询状态。但也要有限重试，避免烧成本。

### 追问 4：哪些工具中断后不能直接重试？

发消息、支付、创建订单、写数据库、提交代码、删除文件、修改生产配置等有副作用工具不能直接重试，必须先查外部状态或要求人工确认。

### 追问 5：`retry_group_id` 和 `tool_call_id` 有什么区别？

`tool_call_id` 更偏协议层，用来把模型 tool call 和 tool result 配对，重试时可能变化；`retry_group_id` 是服务端生成的业务幂等 ID，用来判断同一业务意图是否已经执行。

### 追问 6：Agent 中断后上下文应该恢复哪些内容？

用户目标、当前步骤、已完成内容、中断点、最近工具结果、关键 ID / 路径 / URL、权限状态、失败原因、已尝试方案、下一步候选，以及不能重复的动作。

### 追问 7：如果持久化状态和当前事实冲突怎么办？

优先相信当前事实。持久化状态和 Memory 可能过期，当前工具查询是恢复时的一手事实。必要时标记状态冲突并请求用户确认。

### 追问 8：用户主动停止和系统异常中断有什么区别？

用户主动停止是控制信号，不能默认自动继续；系统异常中断是故障，可以在状态清晰、风险可控时自动恢复。

### 追问 9：多 Agent 场景中断怎么恢复？

父 Agent 要统一维护全局任务状态。子 Agent 失败只返回局部结果，不能自己宣布全局完成。读任务可以并发恢复，写任务必须串行，并用锁、队列或 worktree 隔离共享资源。

### 追问 10：如何让用户感知中断恢复过程？

输出结构化状态：中断阶段、原因、已完成步骤、当前事实、风险判断、下一步动作。如果需要用户确认，要明确说明为什么不能自动继续。

## 8. 背诵版

Agent 中断我会按“原因分层 + 状态恢复 + 幂等控制”来回答。

首先，中断原因不能只归因给模型，要从五层看：模型层可能 API 超时、限流、流式中断或 tool call 参数不完整；Loop 层可能超过最大轮次、token 预算耗尽或触发重复调用熔断；Tool 层可能参数校验失败、权限不足、handler 超时、外部 API 失败；Context 层可能上下文爆掉、压缩丢关键状态；Runtime 层可能 WebSocket 断开、进程重启、状态没持久化或多 Agent 写冲突。

其次，中断后不能直接继续上一次动作，而要先加载持久化 task state，包括用户目标、计划、当前步骤、最近工具调用、权限状态、上下文摘要和幂等 ID。然后重新观察当前事实，比如文件、数据库、远程资源、外部任务现在是什么状态。历史记录恢复意图，当前观察判断事实，冲突时以当前观察为准。

最后，对有副作用的工具要做幂等恢复。执行前由服务端生成 `retry_group_id`，记录预提交状态；恢复时判断外部操作是已执行、未执行还是不确定。已执行就标记完成，未执行可以重试，不确定就停止并请求用户确认。生产级 Agent 的关键不是永远不中断，而是中断后能安全停下、解释清楚，并从正确状态恢复。

## 9. 关键词速记

- 中断原因：模型 / Loop / Tool / Context / Runtime
- 模型层：API 超时、429、5xx、stream broken、tool call incomplete
- Loop 层：max steps、timeout、token budget、loop detection、user stop
- Tool 层：schema、business validation、permission、timeout、side effect unknown
- Context 层：context overflow、compaction loss、stale memory、tool result noise
- Runtime 层：WebSocket、process restart、state lost、multi-agent race
- 恢复流程：识别中断 → 加载状态 → 重新观察 → 判断副作用 → 重建上下文 → 继续/降级/停止
- 幂等恢复：retry_group_id、idempotency key、two-phase commit、external fact check
- 恢复原则：历史恢复意图，当前事实判断状态
- 用户体验：结构化说明中断阶段、当前状态、下一步和风险
