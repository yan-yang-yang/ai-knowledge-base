# 2026-10-21：Transformer、Agent Runtime、Tool 可靠性与 OpenClaw 全流程

> 今日实战面试记录，原四题，补充一题。以下为可复述的参考稿；项目实现部分需按真实经历区分已实现、团队能力与设计建议，不补造线上数据。

## 一、聊聊你对 Transformer 的理解

### 面试官问题

聊聊你对 Transformer 的理解，并说明长上下文下为什么可能出现关键信息利用不稳定的现象。

### 参考回答

Transformer 是以注意力机制为核心的序列建模架构。与 RNN 按时间步逐个处理不同，Transformer 可以并行处理序列中的 token，并通过自注意力建立不同位置之间的依赖关系。

输入 token 表示经过线性映射得到 Query、Key、Value。模型以 Query 和 Key 的缩放点积计算相关性分数，经 Softmax 归一化为注意力权重，再对 Value 加权求和：

```text
Attention(Q, K, V) = softmax(QK^T / sqrt(d_k) + mask) V
```

标准缩放点积注意力不是直接计算文字之间的 cosine 或 sine。Q 与 K 的点积衡量模型学到的表示之间的匹配程度；只有对向量做单位化时，点积才等价于余弦相似度。`sqrt(d_k)` 用于控制分数尺度，避免 Softmax 过度饱和。自回归大模型还会使用因果掩码，使当前位置不能看到后续 token。

上下文变长后，关键信息利用可能变得不稳定，工程上有时称为“注意力稀释”。这不是 Softmax 必然把权重平均分散，也不是单一机制造成的：候选位置变多会加剧竞争；无关或相似内容会产生干扰；远距离信息和位置效应、模型的长上下文训练能力也会影响检索与保留。模型能接收更长上下文，不等于能同等可靠地使用其中每一段信息。

工程上可以通过 RAG 检索相关片段、合理切片、元数据过滤、重排、去重和上下文压缩减少噪声，并用关键证据位于开头/中间/末尾及加入干扰项的测试集验证长上下文表现。KV Cache 主要减少自回归生成时对历史 token 的重复计算，不直接解决信息干扰或注意力稀释。

### 相关追问：多头注意力和位置编码

多头注意力是在多个表示子空间中并行计算注意力，每个头有各自的 Q/K/V 投影，结果拼接后经线性变换。它让模型能够同时利用不同的关联模式，但不能简单说每个头固定对应一种语义。

注意力本身不天然表达 token 顺序，因此需要位置信息。传统 Transformer 可将正弦、余弦位置编码加到 token 表示上；许多现代大模型使用 RoPE，通过按位置旋转 Query 和 Key，使注意力分数包含相对位置信息。sin/cos 属于位置编码相关机制，不是标准注意力用来直接判断文字语义相似度的函数。

## 二、Agent Runtime 和 Workflow 的区别

### 面试官问题

Agent Runtime 和 Workflow 有什么区别？它们之间是什么关系？

### 参考回答

Workflow 描述业务步骤、条件分支和数据流转，重点是“任务怎么编排”。路径通常由代码或配置定义，适合步骤明确、规则稳定、需要可预测执行的任务。

Agent Runtime 是承载 Agent 执行的运行环境，重点是“Agent 如何运行和被管理”。它通常需要组织模型调用、上下文、工具、状态和控制循环，并处理权限、超时、重试、事件、会话和中断等运行时问题。

二者不是互斥替代关系。Runtime 可以运行 Workflow；Workflow 的某些节点也可以调用 Agent 处理需要语言理解或开放式判断的部分。在公共雨伞 AI 客服项目中，可以将订单/设备查询、规则检索、异常分析和结果校验组织为有边界的业务流程；模型负责理解自然语言、抽取信息和辅助分析，应用侧保留业务校验和高风险动作控制。Runtime 则提供模型与工具的执行及状态管理能力。

## 三、Tool 单次成功率 98%，一次任务调用 30 次的失败概率及优化

### 面试官问题

某个 Tool 单次调用成功率为 98%，一次任务调用它 30 次，任务失败概率是多少？如何优化？

### 参考回答

假设 30 次调用相互独立，并且任务要求每次都成功，30 次全部成功的概率是 `0.98^30 ≈ 54.55%`，因此至少一次失败的概率是 `1 - 0.98^30 ≈ 45.45%`。如果失败之间存在相关性，例如依赖服务整体不可用，就不能直接套用独立假设，需要结合实际故障模型估算。

优化上先分类错误：超时、短暂网络故障或限流可以在预算内有限重试；参数错误、权限拒绝等确定性错误不应盲目重试。重试使用指数退避和随机抖动，避免重试风暴。对有副作用的 Tool 使用幂等键或任务 ID，处理“请求超时但服务端可能已成功”的不确定状态时，先查询外部状态再决定是否重试。

此外，记录每次子调用状态和结果，使任务能从部分失败处恢复；无依赖调用可在并发和下游限流允许时并行执行；为整项任务设置总超时、重试预算和熔断。非关键步骤可返回带明确缺失项的部分结果，但缺少必要证据时不能给确定结论或继续高风险动作。最终应关注端到端任务成功率、重试率、延迟和重复副作用，而不只看单次调用成功率。

## 四、项目二：OpenClaw 从用户输入到结果返回的全流程

### 面试官问题

结合基于 OpenClaw 的公共雨伞后台自动化与智能数字人项目，介绍从用户输入问题到结果返回的完整流程。

### 参考回答

用户从客服后台、运营操作台或数字人入口发起请求后，接入层先识别请求来源、用户身份和会话，并将请求路由到相应的 Agent 执行流程。系统根据场景加载对应的 Agent 配置、上下文和可用工具集合；Tool Profile 用来按场景限制工具范围，而不是把所有业务能力一股脑提供给模型。

Runtime 将系统指令、必要的会话历史和本轮输入组装后调用模型。模型可以直接生成答复，也可以提出工具调用请求。提出调用不等于执行：执行侧需要确认工具已注册并可用，校验参数格式，再进行业务规则和权限检查。只读查询通过校验后调用相应业务接口；涉及副作用或高风险的动作则按实际配置进入 dry-run、人工审批或二次确认，获准后才执行。

工具执行结果以结构化信息返回，作为新观察写入 Agent 上下文，Runtime 再驱动模型判断下一步。这个循环持续到产生最终答复、达到轮次或时间限制，或进入需要人工处理的状态。系统随后把答复及必要的结构化状态返回前端；如果采用事件流，前端还可以展示处理中状态、工具调用、审批和执行进展。任务状态和审计信息用于追踪执行过程；发生中断时，系统根据已记录状态判断哪些步骤完成、哪些需要核对或恢复，不能对可能已成功的副作用操作盲目重放。

面试时要按真实架构说清楚职责：OpenClaw Runtime 提供哪些运行能力，BFF/项目应用负责哪些路由与业务编排，业务 Tool 如何访问后台 API，前端如何展示事件。不要把项目侧实现说成 OpenClaw 原生功能，也不要把目标设计说成已经上线。

### 流程速记

用户输入 → 身份/会话与入口路由 → 加载场景配置和工具范围 → 组装上下文并调用模型 → 直接回答或提出 Tool 调用 → 参数/业务/权限检查 → 查询、审批或执行 → 结果回写上下文 → Agent 继续判断 → 返回答复/事件并记录状态与审计。

## 五、大模型请求中断、用户取消与 Agent Runtime 的区别

### 面试官问题

大模型请求中断和用户取消有什么区别？Agent Runtime 分别需要怎么处理？与 LangGraph interrupt 有什么不同？

### 1 分钟回答

大模型请求中断通常是超时、网络断流或模型服务异常，属于单次调用故障；用户取消是明确的任务控制意图，需要停止当前任务的后续执行。Agent Runtime 对前者判断能否有限重试或从已保存的状态恢复，对后者则标记取消、停止调度，并把取消信号传递给模型和工具，不能按普通错误自动重试。

取消不等于回滚。已经提交的退款、关单等操作，需要核对外部系统结果，必要时走补偿或人工确认；只断开 SSE / WebSocket 也不代表后台任务已经停止。LangGraph interrupt 则是保存状态、暂停并等待输入，之后可以通过 resume 继续，与默认终止当前执行意图的取消不同。

### Runtime 处理差异

| 对比项 | 模型请求意外中断 | 用户取消任务 |
| --- | --- | --- |
| 原因 | 超时、断流、模型服务异常 | 用户点击停止或发出取消指令 |
| 用户意图 | 原任务通常仍需完成 | 停止当前任务 |
| 作用范围 | 当前模型调用，可能影响整轮任务 | 当前任务及其所属的模型、工具和待执行步骤 |
| Runtime 行为 | 分类故障，判断重试、降级、恢复或报错 | 记录取消意图，停止调度并传播取消信号 |
| 自动继续 | 满足恢复和重试条件时可以 | 默认不继续，等待用户重新发起 |

模型正常返回结束标记、触及输出上限或安全拒答，也需要各自处理，不能一概归为网络故障。这里的“中断”特指请求意外失败。

### 模型请求中断：恢复执行边界

例如任务依次执行“模型判断 → 查询订单 → 模型分析 → 查询设备 → 生成回复”。如果在模型分析阶段断流，Runtime 应保留已成功的订单查询结果，从合适的步骤恢复，避免整项任务盲目重跑。

- 未完整接收、未通过校验的工具调用参数不能执行。
- 对暂时性故障设置有限重试、退避和总时间预算；重试前检查任务是否已取消。
- 工具调用已发出但返回丢失时，先查询实际执行状态；写操作通过幂等键避免重复副作用。
- 恢复时核对关键业务状态，不能把旧查询结果永远视为当前事实。

### 用户取消：停止调度与协作终止

参考状态流转为 `RUNNING → CANCELLING → CANCELLED`，具体状态命名由应用决定。Runtime 先持久化取消意图，阻止新步骤，再通过取消令牌或 AbortSignal 等机制通知模型、在途工具和所属子任务；工具必须实际支持取消，传播信号不保证底层立即终止。

取消可能与执行完成并发发生，需要在工具派发、重试和结果处理边界再次检查状态，避免迟到的结果重新推进流程。已完成的步骤保留记录；无法终止或结果不确定的操作单独标明，不能向用户承诺“所有业务操作均已撤销”。

### 前端断流、任务取消与人工暂停

- **前端断流**：只表示客户端停止接收数据；后端是否继续由明确的连接策略决定。
- **任务取消**：前端向后端提交与任务 ID 关联的取消请求，后端检查任务归属，再由 Runtime 停止后续调度并报告实际状态。
- **LangGraph interrupt**：暂停工作流、保存可恢复状态并等待人工输入，随后通过 resume 继续；持久化恢复需要配置 checkpointer 和对应线程标识。

不应依赖 Prompt 告诉模型“不要继续”来实现取消，执行控制需要由应用和 Runtime 保证。

### 项目中怎么讲

公共雨伞订单排查中，模型分析超时可以在预算内重试并复用已查证据；用户点击停止后，应阻止新的订单、设备查询和后续业务动作。若退款请求已经提交，则单独核对退款状态并告知用户，不能把停止生成回答等同于取消退款。这里是实现思路，实际面试需按本人已实现范围表达。

### 验证重点

覆盖模型流式断开、工具排队时取消、工具执行时取消、取消与完成并发、迟到结果、取消后重试、写操作超时及不支持取消的工具；检查是否还派发新步骤、是否重复产生副作用，以及前端状态是否如实反映执行结果。

### 背诵版

> 模型请求中断是调用故障，Runtime 负责有边界地重试和恢复；用户取消是任务控制，Runtime 负责停止调度并传播取消。取消不等于回滚，前端断流不等于任务停止，interrupt 则是等待输入后可以恢复的人工暂停。

## 事实与表达边界

- Transformer 的 Q/K 点积不是直接对文字计算 cosine/sine；“注意力稀释”是对长上下文信息利用不稳定的概括，不应描述成 Softmax 必然均分。
- Tool 失败概率 45.45% 依赖“30 次独立且全部必须成功”的假设。
- OpenClaw 全流程中 Runtime、BFF、工具服务和前端各自负责什么，应以项目真实实现为准。
- 不虚构故障案例、上线能力、个人贡献或性能收益；方案建议需明确标注为建议。
